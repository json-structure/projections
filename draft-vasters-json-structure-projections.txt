Abstract

   This document projects the representation-neutral JSON Structure
   model into JSON Schema, Apache Avro, Protocol Buffers, XML Schema,
   and Concise Data Definition Language (CDDL).  It defines target
   schemas, serializer value bindings, reverse imports, and conditions
   for preserving values, constraints, and schema information.

1.  Introduction

   JSON Structure [JSTRUCT-CORE] is intended as a representation-neutral
   definition language.  Its schemas are written in JSON [RFC8259] and
   include provisions for JSON serialization, but its data definitions
   can be used independently of that representation.

   JSON Structure serves as the canonical, abstract base model for data
   definitions.  Data structures are defined in JSON Structure and
   projected into programming languages, database schemas, and other
   schema languages.  This document covers projections into formal
   schema languages.

   To serialize data in Avro, an application projects its JSON Structure
   data definition into an Avro schema and uses an Avro serializer with
   that schema.  The same approach applies to Protocol Buffers and the
   other formats covered here: their schemas are projections of the data
   model contained in the JSON Structure definition.  Reverse imports
   recover JSON Structure definitions within the stated preservation
   limits.

   The targets are JSON Schema [JSONSCHEMA-CORE]
   [JSONSCHEMA-VALIDATION], Avro [AVRO], Protocol Buffers [PROTO2]
   [PROTO3], XML Schema (XSD) [XSD-STRUCTURES] [XSD-DATATYPES], and CDDL
   [RFC8610].

   The rules use Validation [JSTRUCT-VALIDATION], Conditional
   Composition [JSTRUCT-COMPOSITION], and Alternate Names
   [JSTRUCT-ALTNAMES] where needed.

2.  Conventions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   The _model_ is the canonical data model defined by a JSON Structure
   schema document.  A _projection_ maps that model into another schema
   language. _Source_ and _target_ follow the conversion direction.  A
   _binding_ maps model values to and from the serializer's data API.  A
   _carrier_ holds a value lacking an equivalent target type.
   Projection rules specify schema mappings, bindings, and preservation
   limits.

   The applicable Core version is identified by $schema.  A processor
   MUST report any substitution of another version's semantics.

3.  Projection and Preservation Model

3.1.  Canonical Definitions and Serialization Bindings

   A projection MUST specify target schemas and bindings from logical
   types, not JSON tokens.  Decimals are exact base-10; binary values
   are octets.

   Native types SHOULD be used when value-preserving.  Textual or
   wrapped carriers require a target or serializer limitation, or an
   explicit representation-preserving profile.  The reason and
   consequences MUST be stated.  The model remains authoritative: a
   binding or identified validator MUST enforce constraints absent from
   the target when preservation is claimed.  Validation outside the
   generated target schema is called _residual validation_.

   Core JSON encodings apply only to selected JSON representations or
   boundaries, including JSON Schema and the CDDL JSON profile.  They
   MUST NOT be imposed on native bindings.

3.2.  Instances and Value Equivalence

   Let S be the set of valid source values and T the set of target
   values.  Encoding E maps S into T; decoding D maps target values back
   to the source model.  Value preservation requires D(E(x)) = x for
   every x in S.

   Equality follows the source model: object and set order is
   irrelevant; array and tuple order matters.  Absence, present null,
   and present empty collections differ.  Numeric equality is exact;
   binary equality compares octets; string equality compares characters.

   Logical values MUST be distinguished from lexical spellings.
   Trailing decimal zeroes, equivalent binary-text spellings, token
   whitespace, XML prefixes, unordered schema members, and comments need
   not survive unless lexical or source-file preservation is requested.

   Temporal bindings MUST identify calendar, offset-bearing, or instant
   semantics.  Discarding an observable offset loses information.  An
   explicit instant profile permits UTC normalization, without
   preserving original text.

3.3.  Independent Preservation Properties

   Value preservation:  Every valid source value is reversible, even if
      its carrier changes.

   Constraint preservation:  The target schema accepts exactly the
      encodings of valid source values, E(S), with no additional values.
      Constraints checked only by an adapter are not native target-
      schema constraints.

   Schema round-trip preservation:  Import recovers semantic
      declarations: types, references, names, constraints, defaults, and
      identities.  Claims MUST state required metadata.

   Unqualified _lossless_ requires all three for the stated subset and
   profile.  Partial claims MUST be qualified.  For example, int8 in
   unrestricted Avro int preserves values, widens constraints, and needs
   metadata to recover width.

3.4.  Processing Profiles and Diagnostics

   A processor MUST identify dialects, roots, extensions, and required
   adapters, validators, or metadata.  Unmet lossless requests MUST
   fail; explicitly enabled lossy projections MAY proceed.  Every
   applicable loss MUST be reported at its affected source location.
   Every loss diagnostic MUST identify source format and location,
   target construct or omission reason, affected preservation property,
   effect, and any remedy or source restriction.  Effects distinguish
   widening (admitting additional values), narrowing (excluding source
   values), value collapse (merging distinct values), representation
   change, and schema loss.

   Ignored annotations MUST NOT count as enforcement.  Unknown types and
   unresolved references MUST NOT silently become permissive types or
   defaults.  Diagnostic interfaces and metadata formats are
   implementation-defined; interoperable round-trip claims MUST use an
   agreed metadata channel and interpretation.

3.5.  Roots, Namespaces, and References

   Processors MUST select root type or $root; definitions-only libraries
   MUST NOT acquire arbitrary roots.  A target requiring one root needs
   explicit selection.  References use {"type":{"$ref":"..."}}, or
   {"$ref":"..."} inside union arrays.  Bare schema $ref and referenced
   root type are invalid; referenced roots use $root.

   References MUST resolve before name rewriting, with JSON Pointer
   escaping per [RFC6901] and identity preserved.  Supported recursion
   MUST remain references; unsupported recursion MUST be diagnosed, not
   depth-truncated.  External resources MAY be materialized or use
   Import [JSTRUCT-IMPORT]; resource identity and resolution MUST
   survive.

3.6.  Names and Annotations

   Imported names MUST map to distinct legal JSON Structure identifiers
   matching [A-Za-z_][A-Za-z0-9_]*. A declaration's altnames map MAY
   retain names for other representations.  Its json entry gives the
   JSON property name; avro, proto, xml, and cddl give format-specific
   names.  A projection uses the entry for its target format.

   For example, this schema gives the model property firstName different
   JSON and Avro names:

   {
     "$schema": "https://json-structure.org/meta/extended/v0/#",
     "$id": "https://example.com/schemas/Person",
     "$uses": ["JSONStructureAlternateNames"],
     "name": "Person",
     "type": "object",
     "properties": {
       "firstName": {
         "type": "string",
         "altnames": {
           "json": "first-name",
           "avro": "first_name"
         }
       }
     },
     "required": ["firstName"],
     "additionalProperties": false
   }

   The Avro record field is named first_name; the JSON property is
   first-name.  The model's required array still names firstName.
   Alternate names specify spelling, not encoding, field numbers, XML
   node kinds, or namespace identity.  Target names MUST satisfy the
   format's naming and uniqueness rules.

   required and tuple name declaration keys; references MUST be
   rewritten consistently. altenums mappings MUST be one-to-one.
   Descriptions SHOULD be copied to target documentation.  Examples,
   units, currencies, localized descriptions, semantic annotations, and
   unknown extensions MUST be retained as metadata or reported lost.

3.7.  Numeric and Textual Representations

   integer aliases int32.  A b-bit signed integer spans -(2^(b-1))
   through 2^(b-1)-1; an unsigned integer spans 0 through 2^b-1.

   +=======+========================================+=======================================+
   |Type   |                                 Minimum|                                Maximum|
   +=======+========================================+=======================================+
   |int8   |                                    -128|                                    127|
   +-------+----------------------------------------+---------------------------------------+
   |uint8  |                                       0|                                    255|
   +-------+----------------------------------------+---------------------------------------+
   |int16  |                                  -32768|                                  32767|
   +-------+----------------------------------------+---------------------------------------+
   |uint16 |                                       0|                                  65535|
   +-------+----------------------------------------+---------------------------------------+
   |int32, |                             -2147483648|                             2147483647|
   |integer|                                        |                                       |
   +-------+----------------------------------------+---------------------------------------+
   |uint32 |                                       0|                             4294967295|
   +-------+----------------------------------------+---------------------------------------+
   |int64  |                    -9223372036854775808|                    9223372036854775807|
   +-------+----------------------------------------+---------------------------------------+
   |uint64 |                                       0|                   18446744073709551615|
   +-------+----------------------------------------+---------------------------------------+
   |int128 |-170141183460469231731687303715884105728|170141183460469231731687303715884105727|
   +-------+----------------------------------------+---------------------------------------+
   |uint128|                                       0|340282366920938463463374607431768211455|
   +-------+----------------------------------------+---------------------------------------+

                                  Table 1

   Core JSON uses numbers through uint32, strings for wider integers and
   decimal, and encoded text such as Base64 [RFC4648] for octets.
   Schema numeric constraints follow those representations but MUST be
   applied numerically.  Signed integer strings match -?(0|[1-9][0-9]*),
   unsigned strings (0|[1-9][0-9]*), over the entire string; bounds
   remain additional.

   Core decimals require a fractional part.  Projections MUST apply
   effective precision and scale, defaulting to 34 significant and 7
   fractional digits.  These MUST be reconciled with target coefficient-
   digit or fixed-scale rules.

   Generic number MUST NOT be assumed binary64.  Floating conversion
   preserves only exactly representable values; overflow, underflow, and
   rounding lose values. float8 specifies no portable E4M3, E5M2, or
   binary16 encoding; processors MUST NOT infer one.  Wider carriers
   lose type identity.  Reverse projections MUST handle NaN, payloads,
   and infinities separately.

   Character lengths, decoded octet lengths, encoded byte lengths, and
   numeric precision MUST NOT be interchanged.

3.8.  Presence, Defaults, and Composition

   For non-null T:

         +================+=====================================+
         | Declaration    | Permitted states                    |
         +================+=====================================+
         | Required T     | A present non-null value            |
         +----------------+-------------------------------------+
         | Optional T     | Absence or a present non-null value |
         +----------------+-------------------------------------+
         | Required union | A present null or non-null value    |
         | of null and T  |                                     |
         +----------------+-------------------------------------+
         | Optional union | Absence, a present null, or a       |
         | of null and T  | present non-null value              |
         +----------------+-------------------------------------+

                                 Table 2

   Presence states MUST remain distinct.  Default application MUST be
   evaluated separately; defaults do not imply nullability.

   Core unions select the first matching member when several members
   accept a value.  Losing that branch identity affects round trips.  An
   inclusive union accepts any matching branch; an exclusive union
   requires exactly one match.  Inclusive unions MUST NOT become
   exclusive unless disjoint.  Alternative required sets mean exactly
   one complete set; projections MUST preserve this condition, not
   flatten the sets.

   Materialization expands inherited declarations into explicit
   properties.  Inheritance and add-ins MUST follow source semantics.
   Materialization MAY be used after Core's first-base-wins property
   precedence.  Derived properties MUST NOT redefine inherited
   properties.  Conjunctive constraints MUST remain conjunctive without
   replacing that precedence.  Unrepresentable abstractness,
   inheritance, or add-in identity MUST be reported.

4.  JSON Schema

   This projection validates Core JSON representations using Draft
   2020-12.  Earlier dialects MUST be normalized, including Draft-07
   tuple items, additionalItems, definitions, and older boolean
   exclusiveMinimum.

4.1.  JSON Structure to JSON Schema

4.1.1.  Primitive Types

   Targets MUST identify the 2020-12 $schema.  Table mappings include
   the qualifications below.

    +==============================+=================================+
    | JSON Structure type          | JSON Schema representation      |
    +==============================+=================================+
    | null                         | {"type":"null"}                 |
    +------------------------------+---------------------------------+
    | boolean                      | {"type":"boolean"}              |
    +------------------------------+---------------------------------+
    | string                       | {"type":"string"}               |
    +------------------------------+---------------------------------+
    | number                       | {"type":"number"}               |
    +------------------------------+---------------------------------+
    | integer, int8, uint8, int16, | integer with the inclusive      |
    | uint16, int32, uint32        | bounds in Section 3.7           |
    +------------------------------+---------------------------------+
    | int64, uint64, int128,       | string with the integer grammar |
    | uint128                      | and the applicable bounds       |
    +------------------------------+---------------------------------+
    | float8, float, double        | number, with source-domain      |
    |                              | restrictions when expressible   |
    +------------------------------+---------------------------------+
    | decimal                      | string with the decimal         |
    |                              | grammar, precision, and scale   |
    +------------------------------+---------------------------------+
    | binary                       | string with contentEncoding and |
    |                              | optional contentMediaType       |
    +------------------------------+---------------------------------+
    | date                         | string, format: "date"          |
    +------------------------------+---------------------------------+
    | datetime                     | string, format: "date-time"     |
    +------------------------------+---------------------------------+
    | time                         | string, format: "time"          |
    +------------------------------+---------------------------------+
    | duration                     | string, format: "duration"      |
    +------------------------------+---------------------------------+
    | uuid                         | string, format: "uuid"          |
    +------------------------------+---------------------------------+
    | uri                          | string, format: "uri-reference" |
    +------------------------------+---------------------------------+
    | jsonpointer                  | string, format: "json-pointer"  |
    +------------------------------+---------------------------------+
    | any                          | An unconstrained schema, such   |
    |                              | as {} or true                   |
    +------------------------------+---------------------------------+

                                 Table 3

   Numeric keywords do not constrain strings; string-valued bounds MUST
   NOT be copied into them.  Integer-string ranges MAY use exact regular
   expressions; otherwise their bounds MUST be retained for additional
   validation and native widening reported.  Decimal grammar, precision,
   scale, and bounds require equivalent enforcement.  A numeric carrier
   is a separate instance-transforming profile.

   By default, format is an annotation; its presence does not require a
   validator to check that format.  Extended types need an agreed
   assertion profile or equivalent constraints; otherwise their domains
   widen. uri-reference preserves Core's relative references; uri
   excludes them.

   Content annotations do not require decoding or validation.  Core's
   default binary encoding MUST be explicit. contentCompression requires
   metadata or a loss report.

4.1.2.  Objects, Maps, and Collections

   Objects recursively map properties and required using JSON alternate
   names.  Effective additionalProperties MUST be explicit, including
   version-defined defaults and recursively projected schema values.
   Alternative required sets MUST add oneOf branches {"required": Ri} to
   the common object schema.  Ri denotes one alternative set of required
   property names.

   Maps use object without declared properties and projected values as
   additionalProperties. keyNames becomes propertyNames; patternKeys
   becomes patternProperties only with equivalent additional-property
   behavior.

   Arrays project items; sets add uniqueItems: true, without suppressing
   observable JSON array order.  Tuples use prefixItems in tuple order
   and MUST set minItems: n, maxItems: n, and items: false.  Names need
   metadata.

4.1.3.  Unions and Choices

   Unions use anyOf.  Equivalent unrestricted alternatives MAY use a
   type array.  Branch order SHOULD survive; JSON Schema validation does
   not assign Core's first-match identity.

   Tagged choices use oneOf branches with properties: {k: V}, required:
   [k], and additionalProperties: false.  Inline choices use
   materialized alternatives; each MUST require its selector and
   constrain it with const.  Base and branch properties MUST be combined
   before closure.

4.1.4.  Constraints, Definitions, and Defaults

   These keywords map directly only with matching applicability,
   representation, and evaluation: minimum, maximum, exclusiveMinimum,
   exclusiveMaximum, multipleOf, minLength, maxLength, pattern,
   minItems, maxItems, uniqueItems, contains, minContains, maxContains,
   minProperties, maxProperties, dependentRequired, and propertyNames.

   Map entry bounds become property bounds; const and enum retain JSON
   values.  Constraints MUST intersect intrinsic type domains.
   Conditional Composition MAY use corresponding allOf, anyOf, oneOf,
   not, if, then, and else with recursively equivalent evaluation.

   Definitions become uniquely keyed $defs; processors MUST rewrite
   references and MUST NOT emit namespace-only objects as unconstrained
   definitions. $root becomes $ref; $id survives when resource identity
   remains valid. name MAY supply title, not type identity; descriptions
   map directly. $uses, $offers, abstractness, and namespaces need
   metadata.

   JSON Schema default annotates; Validation defaults fill missing
   properties.  This behavioral difference MUST be reported or
   implemented by a declared adapter.

4.2.  JSON Schema to JSON Structure

4.2.1.  Primitive and Numeric Inference

   null, boolean, string, and number map directly.  Integer import MUST
   compute the effective domain, select a containing Core type, and
   retain narrower constraints.  Wide types change JSON numbers to
   strings.  Domains outside all Core integer types MUST be rejected in
   constraint-preserving Core-only requests; other profiles can use an
   explicit numeric-text adapter.

   Integral 1, 1.0, and 1e0 satisfy JSON Schema integer validation.
   Processors MUST distinguish parsed-value preservation from Core's
   lexical integer restrictions.  Numeric formats MUST NOT independently
   justify narrowing or representation changes.  String formats MAY
   select extended types only when asserted and domain-compatible;
   otherwise they remain annotations.  Absolute uri restrictions MUST
   survive.  Digit strings MUST remain strings without declared numeric
   semantics.

4.2.2.  Structural Mapping

   Declared properties become an object; dynamic objects become maps.
   Unconstrained objects use map-of-any.  An object that permits no
   properties, whose only value is {}, uses Validation maxEntries: 0,
   not null.  Undeclared required names need any declarations plus
   applicable pattern and additional-property constraints.

   JSON Schema excludes pattern-matched keys from additionalProperties;
   Core patterns do not declare properties.  Processors MUST construct
   equivalent key/value rules or diagnose unsupported combinations.
   Multiple pattern matches intersect.

   Homogeneous arrays remain arrays, retaining uniqueness constraints.
   Conversion to sets MAY occur only under an explicit order-discarding,
   value-collapsing profile. prefixItems becomes a tuple only with exact
   length and no tail; names MUST be generated or recovered.  Other
   prefixes MUST retain equivalent rules or be rejected, not fixed-
   length by assumption.

4.2.3.  Composition and Unsupported Evaluation Features

   true becomes any; false requires rejection or Conditional Composition
   {"type":"any","not":{"type":"any"}}. Missing type MUST preserve
   category-specific keyword applicability and unconstrained categories.

   anyOf MAY become a type union when all branches declare types and
   selection adds no observable distinction. oneOf needs disjointness
   for inclusive conversion; required-set forms follow Section 4.1.2.
   allOf MUST retain intersections, including contradictions; structural
   merging requires equivalence, never property overwrites.

   $dynamicRef, $dynamicAnchor, unevaluatedProperties, and
   unevaluatedItems MUST be transformed equivalently for the selected
   graph or rejected in lossless mode.  References, anchors, nested $id,
   and vocabularies MUST resolve before conversion.  Unknown required
   vocabularies prevent lossless claims.

4.3.  Example and Preservation Boundary

   This closed object:

   {
     "$schema": "https://json-structure.org/meta/core/v0/#",
     "$id": "https://example.com/schemas/Reading",
     "name": "Reading",
     "type": "object",
     "properties": {
       "label": { "type": "string" },
       "level": { "type": "uint8" },
       "note": { "type": ["null", "string"] }
     },
     "required": ["label", "level"],
     "additionalProperties": false
   }

   projects to:

   {
     "$schema": "https://json-schema.org/draft/2020-12/schema",
     "$id": "https://example.com/schemas/Reading",
     "title": "Reading",
     "type": "object",
     "properties": {
       "label": { "type": "string" },
       "level": { "type": "integer", "minimum": 0, "maximum": 255 },
       "note": { "anyOf": [{ "type": "null" }, { "type": "string" }] }
     },
     "required": ["label", "level"],
     "additionalProperties": false
   }

   Presence and bounds survive; recovering original width requires
   metadata.

5.  Apache Avro

   This section uses Avro 1.12.0 [AVRO], excluding remote procedure
   calls, container compression, and registry identifiers.  Non-record
   roots are legal; wrappers for surrounding-system restrictions MUST be
   separately declared.

5.1.  JSON Structure to Avro

5.1.1.  Primitive Types

   +==============+=============================+======================+
   | JSON         | Avro carrier                | Qualification        |
   | Structure    |                             |                      |

   +--------------+-----------------------------+----------------------+
   | string       | string                      | Same Unicode text    |
   |              |                             | values               |
   +--------------+-----------------------------+----------------------+
   | integer,     | int                         | Same signed 32-bit   |
   | int32        |                             | domain               |
   +--------------+-----------------------------+----------------------+
   | int8, int16, | int                         | Source range is not  |
   | uint8,       |                             | enforced natively    |
   | uint16       |                             |                      |
   +--------------+-----------------------------+----------------------+
   | uint32       | long                        | Full value domain    |
   |              |                             | fits; unsigned bound |
   |              |                             | is not native        |
   +--------------+-----------------------------+----------------------+
   | int64        | long                        | Native signed 64-bit |
   |              |                             | integer              |

   |              | "decimal"                   | 0; retain unsigned   |

   | int128       | bytes with logicalType:     | Precision 39, scale  |

5.1.2.  Wide Integers

   The standard projection MUST use decimal on bytes, scale 0, precision
   20 for uint64 and 39 for either 128-bit type.  The exact integer is
   the unscaled coefficient: signed big-endian two's complement,
   including a leading zero octet when needed for a positive value.
   Avro supplies the byte-count prefix.

   {
     "type": "record",
     "name": "WideIntegers",
     "namespace": "example",
     "fields": [
       {
         "name": "unsigned64",
         "type": {
           "type": "bytes", "logicalType": "decimal",
           "precision": 20, "scale": 0
         }
       },
       {
         "name": "signed128",
         "type": {
           "type": "bytes", "logicalType": "decimal",
           "precision": 39, "scale": 0
         }
       },
       {
         "name": "unsigned128",
         "type": {
           "type": "bytes", "logicalType": "decimal",
           "precision": 39, "scale": 0
         }
       }
     ]
   }

   A declared fixed profile MAY substitute at least 9 octets for
   precision 20 or 17 for precision 39.  A 16-octet precision-39
   declaration is invalid.  Bindings or validators MUST enforce original
   bounds, including unsigned non-negativity.  Unsupported precision
   MUST fail, not round, truncate, or pass through binary64.
   Reconstruction MUST retain integer identity and bounds; decimal
   parameters cannot distinguish the two 128-bit types.

5.1.3.  Logical Types

   Logical types MUST use their specified carriers: decimal on bytes/
   fixed, date and time-millis on int, timestamps on long.  Unknown
   annotations are ignored by ordinary readers.

   An Avro decimal has precision p and scale s; its value is coefficient
   times 10^(-s).  Projections MUST derive compatible p > 0 and 0 <= s
   <= p from effective source constraints, without rounding; otherwise
   they MUST declare an alternative carrier or reject lossless native
   conversion.  Decimal text needs numeric validation.

   For n-octet fixed, precision cannot exceed floor(log10(2^(8*n-1)-1)).
   Size, padding, and sign extension MUST conform.  Core decimal output
   MUST restore a fractional part, including .0 at scale zero; lexical
   zeroes need not survive.

   *  date: signed days since 1970-01-01, within both calendar domains.

   *  time-millis/time-micros: offset-free time since midnight; Core
      full-time has an offset.  Dropped offsets or fractions are losses.

   *  timestamp-millis/timestamp-micros/timestamp-nanos: signed epoch
      counts.  Bindings MUST check range, precision, and leap seconds
      under a declared instant policy; original offsets and text do not
      survive.

   *  local-timestamp-millis/local-timestamp-micros/local-timestamp-
      nanos: no zone; UTC MUST NOT be assumed.

   *  duration: unsigned little-endian uint32 months, days, and
      milliseconds in 12 octets, not a general signed duration.

   Unmatched temporal bindings MUST identify preserved components and
   validate temporal text.

5.1.4.  Records, Optionality, and Collections

   Objects become records, properties become fields, and namespaces
   remain distinct.  Recursive records MUST follow legal Avro definition
   order.  Open objects need an extra-properties map with externally
   enforced collision exclusion; Avro records have no
   additionalProperties.

   Every field has a value.  For non-null T:

   +=================+================================================+
   | Source property | Avro field representation                      |
   +=================+================================================+
   | Required T      | T                                              |
   +-----------------+------------------------------------------------+
   | Required        | Union of null and T                            |
   | nullable T      |                                                |
   +-----------------+------------------------------------------------+
   | Optional T      | Union of null and T; null represents absence   |
   +-----------------+------------------------------------------------+
   | Optional        | Union of null and a named present-value record |
   | nullable T      | whose value field has union type null and T    |
   +-----------------+------------------------------------------------+

                                 Table 5

   In the last row, outer null means absence.  A present record whose
   value is null means present null.

   Wrapper names MUST be unique.  Optional fields MAY default to null
   with null first.  Optional-nullable flattening to ["null", T] MUST
   report value collapse; other null-as-absence bindings require source
   correspondence.

   Arrays and string-keyed maps project recursively.  Sets use arrays
   with external uniqueness; collection bounds need validation.  Tuples
   use fields in tuple order; names and order MUST survive, without
   inferring object identity.

5.1.5.  Unions, Choices, and Enumerations

   Direct nested unions and duplicate unnamed branch kinds require
   distinct named record wrappers.  Processors MUST add these where
   necessary and apply Core first-match selection before choosing the
   Avro branch.

   Tagged choices SHOULD use distinct named one-field records, unwrapped
   on import.  A discriminator plus independent union needs correlation
   validation.  Inline choices use materialized branch records;
   selectors MUST be restored.  Defaults do not enforce selector
   constants.

   String enums require legal unique symbols or reversible mappings.
   Numeric enums MUST NOT become symbols without explicit
   transformation. const, patterns, lengths, narrower bounds, required-
   set alternatives, and composition generally need validation beyond
   Avro.

5.1.6.  Extensible Values and Schema Evolution

   The projection of any uses different reader and writer schemas.  The
   generic reader includes an empty named record in its union.  A
   concrete writer adds typed fields to that record without changing the
   reader.  Primitive, array, or map branches MAY predeclare understood
   categories; they do not close the source domain.

   Union order and promotions matter: string can resolve as bytes, or
   vice versa.  Value-preserving bindings MUST use named wrappers or
   retain writer-branch identity and its exact inverse, not infer
   categories from resolved values.

   Each extensible position MUST have a stable unique full name; writers
   MUST retain it and enclosing reader compatibility.  Unmatched new
   union branches fail resolution.  Written fields MUST have concrete
   types; decoding MUST use the actual writer schema as well as the
   reader.

   This reader uses the extension record for binary and collection
   values:

   {
     "type": "record",
     "name": "Message",
     "namespace": "example",
     "fields": [
       { "name": "id", "type": "long" },
       {
         "name": "payload",
         "type": [
           "null", "boolean", "int", "long",
           "float", "double", "string",
           {
             "type": "record",
             "name": "Message_payload_AnyValue",
             "fields": []
           }
         ]
       }
     ]
   }

   A later writer adds typed payload fields:

   {
     "type": "record",
     "name": "Message",
     "namespace": "example",
     "fields": [
       { "name": "id", "type": "long" },
       {
         "name": "payload",
         "type": [
           "null", "boolean", "int", "long",
           "float", "double", "string",
           {
             "type": "record",
             "name": "Message_payload_AnyValue",
             "fields": [
               { "name": "label", "type": "string" },
               {
                 "name": "counter",
                 "type": {
                   "type": "bytes", "logicalType": "decimal",
                   "precision": 20, "scale": 0
                 }
               }
             ]
           }
         ]
       }
     ]
   }

   The reader retains id but skips label and counter.  New-writer/old-
   reader compatibility needs no defaults; new-reader/old-writer
   requires defaults for missing required reader fields.

   Bindings MUST specify extension-field and synthetic-wrapper meanings,
   select the intended branch, and encode all data under the actual
   writer schema, without rounding to fit floating branches.  Every
   value MUST conform to that schema; schema changes require
   identification or framing.

   Skipped fields are lost even when the decoder knows the writer
   schema.  The empty result MUST NOT claim canonical reconstruction
   without independent evidence.  Value-preserving imports or relays
   MUST decode writer fields with a writer-aware binding or retain the
   encoded datum and writer schema.

5.2.  Avro to JSON Structure

5.2.1.  Types and Names

   Primitives map directly, except int -> int32, long -> int64, and
   bytes -> binary.  Non-finite values need tagged representations or
   rejection of the source domain; finite-only restrictions MUST be
   reported.

   Records become closed objects with every field required, including
   nullable or defaulted fields.  Empty records use map-of-any with
   Validation maxEntries: 0; identifying original any needs retained
   correspondence.

   Arrays, maps, and named references map directly after full-name
   resolution.  Enums become string enums; round trips retain symbol
   order. fixed becomes binary with exact octet count; maxLength MUST
   NOT claim to reconstruct that binary size.

   Unions MAY become Core unions without required identity loss;
   otherwise tagged choices MUST retain branches, including int/long
   distinctions for equal values.  Array/map union members require
   reusable type references.

5.2.2.  Logical Types and Resolution Metadata

   Retained wide-integer bindings MUST recover the declared integer type
   after checking precision, scale, integrality, and bounds.  Otherwise
   decimal import MUST preserve bounds +/-(10^p-1)*10^(-s) and quantum
   10^(-s).  The quantum is the difference between adjacent
   representable decimal values.  One exact construction uses Core
   precision p for s > 0, p+1 for s = 0, scale max(1,s), those bounds,
   and Validation multipleOf equal to the quantum.  For p=2, s=2, bounds
   are -0.99..0.99 and quantum 0.01.  Decimal constraints retain
   fractional syntax, including .0; documents MUST declare
   JSONStructureValidation in $uses.  Unsupported parameters MUST be
   diagnosed, not narrowed.

   Round trips MUST retain carrier size and logical identity. big-
   decimal MUST use declared variable-scale semantics or report
   restriction.  UUIDs require shared domains; fixed 16-octet versus
   textual carriers need metadata.  Dates MAY use the shared calendar
   domain; timestamps MAY use explicit UTC formatting with unsupported
   ranges/fractions rejected or diagnosed.  Timezone-free types MUST NOT
   invent offsets.  Durations MAY use uint32 month/day/millisecond
   objects or tuples; duration text needs semantic and range
   equivalence.

   Unknown logical types MUST retain underlying types and annotations;
   malformed annotations MUST NOT justify recognized Core types.
   Aliases, field/sort order, enum/field defaults, and resolution rules
   need metadata.  Resolution defaults do not permit omitted writer
   fields; conversion to Validation defaults MUST qualify behavioral
   changes.  Byte/fixed defaults MUST be decoded by Avro's rules before
   Core encoding.

5.3.  Example and Preservation Boundary

   This model has an int64 identifier and required nullable note:

   {
     "$schema": "https://json-structure.org/meta/core/v0/#",
     "$id": "https://example.com/schemas/Contact",
     "name": "Contact",
     "$root": "#/definitions/example/Contact",
     "definitions": {
       "example": {
         "Contact": {
           "name": "Contact",
           "type": "object",
           "properties": {
             "id": { "type": "int64" },
             "note": { "type": ["null", "string"] }
           },
           "required": ["id", "note"],
           "additionalProperties": false
         }
       }
     }
   }

   Its Avro projection is:

   {
     "type": "record",
     "name": "Contact",
     "namespace": "example",
     "fields": [
       { "name": "id", "type": "long" },
       { "name": "note", "type": ["null", "string"] }
     ]
   }

   id is supplied as an integer; note selects null or string.  An Avro
   default would not make note optional.

6.  Protocol Buffers

   Generation uses proto3 [PROTO3] with explicit presence; import also
   covers proto2 [PROTO2].  Editions features MUST resolve explicitly,
   not inherit proto3 presence or enum assumptions.  Mappings MUST
   distinguish decoded-message values, binary layout, and ProtoJSON
   [PROTOJSON].  Services and methods are outside scope.

   restrictions.

   Timestamp bindings MUST declare instant semantics and check year
   range, nanoseconds, offset normalization, and leap seconds without
   truncation or invented offsets.  Observable offsets need component
   carriers.  Explicit temporal-text bindings MAY address native type
   gaps.

6.1.2.  Messages and Presence

   Objects become messages.  Scalars use explicit presence (optional T);
   unset means absence, set includes zero, false, and empty string
   [PROTO-PRESENCE].  Required scalars MUST additionally be checked for
   presence.  Message fields already track presence and MUST NOT become
   implicitly present empty objects.

   Nullable properties SHOULD use a wrapper with null and value oneof
   arms.  Wrapper absence, selected null, and selected value represent
   the three states.  Bindings MUST reject present wrappers with unset
   arms, require wrappers for required properties, and report these non-
   native checks.

   Primitive wrappers lack present null.  ProtoJSON parsing MUST NOT
   claim presence distinctions absent from decoded messages.  Open
   objects need separate extra-property maps or entry lists with
   collision checks; unknown numbered wire fields are not string-keyed
   additional properties.

6.1.3.  Collections, Tuples, and Choices

   Arrays use repeated; nested collections MUST use message wrappers.
   Nullable items also need wrappers.  Optional arrays/maps need outer
   presence wrappers; required collections materialize empty values.
   Maps use map<string,V> with legal or wrapped values; order is
   irrelevant.  Set uniqueness and collection bounds need validation.

   Tuples use named message fields, retained positional order, and
   member-presence validation; field numbers do not declare tuple order.

   Tagged choices use oneof fields, with repeated/map alternatives
   wrapped.  Bindings MUST restore tags and reject unset groups when
   choice values are present: oneof enforces at most one, not exactly
   one.  Inline choices also restore/check selectors after inheritance.
   Core unions need declared first-match selection and reversible
   wrappers, not independent optional fields.

6.1.4.  Field Numbers and Enumerations

   Fields MUST receive unique numbers 1..536870911 except 19000..19999.
   Correspondences MUST survive; removed numbers MUST be reserved, not
   reused.  Initial allocation MAY use lowest available numbers in
   lexicographic identifier order; this is not an evolution policy.

   Round trips retain packages, nested scopes, JSON names, reservations,
   and integer encodings.  String enums require explicit symbol/number
   mappings.  Proto3 requires an initial zero symbol and admits unknown
   numbers; extra values need validation.  Assignments and symbols MUST
   survive round trips, and widening MUST be diagnosed.  Numeric aliases
   lose spelling identity.

   Constants, narrower bounds, patterns, lengths, requiredness,
   uniqueness, and composition need extra validation.  Custom options
   MUST identify vocabulary and enforcing processors; they are not
   standalone proto3 constraints.

6.2.1.  Scalar and Enum Mapping

6.2.2.  Presence and Compound Mapping

   Proto2 required fields become required properties; optional fields
   remain optional non-null, including defaulted scalars.  Reading a
   getter's default value does not make an unset field present.
   Validation defaults instead create missing properties.

   Proto3 explicit presence maps unset/set to absent/present.  Implicit
   scalars materialize effective values as required properties;
   omission-of-defaults profiles MUST be declared without claiming
   original wire presence.  Repeated/map fields become required arrays/
   maps, materializing empties.  Typed keys need reversible canonical
   strings and MUST retain signedness, bounds, and boolean true/false
   spellings.

   Real oneof groups become optional tagged choices named by fields;
   unset means absent.  Synthetic proto3-optional groups MUST NOT become
   choices.  These descriptor-only oneofs track scalar presence, not
   application choices.  Declared-field messages become closed objects;
   empty messages use map-of-any, Validation maxEntries: 0, not null.
   Preserved unknown wire fields require an additional numbered-field
   representation.

6.2.3.  Well-Known Types and ProtoJSON

   Full google.protobuf identities govern well-known types:

   *  NullValue: null with enclosing presence preserved.

   *  Timestamp: UTC datetime; range, nanoseconds, and normalization
      MUST be checked.

   *  Duration: signed seconds/nanoseconds with bounds and consistent
      signs; calendar text needs a declared profile.

   *  Struct, ListValue, Value: JSON-like maps, arrays, and values;
      numeric values use binary64.

   *  Any: retain type URL and serialized message, or resolve and
      project the typed payload; it MUST NOT become unconstrained JSON.

   ProtoJSON uses strings for 64-bit integers and enum symbols, Base64
   for bytes, and json_name or derived names.  Its accepted input
   grammar differs from Core.  Mappings MUST distinguish input syntax,
   canonical output, and decoded values; JSON null may leave fields
   unset.

6.3.  Examples and Preservation Boundary

   Required id and optional labels use:

   syntax = "proto3";
   package example;

   message Labels {
     repeated string values = 1;
   }

   message Packet {
     optional uint64 id = 1;
     Labels labels = 2;
   }

   Unset labels means absence; present empty Labels means an empty
   array.  Validation requires id presence.

   Conversely:

   syntax = "proto3";
   package example;

   message Reply {
     oneof result {
       string text = 4;
       uint32 count = 9;
     }
   }

   The declared-field import is:

   {
     "$schema": "https://json-structure.org/meta/core/v0/#",
     "$id": "https://example.com/schemas/Reply",
     "name": "Reply",
     "type": "object",
     "properties": {
       "result": {
         "name": "ReplyResult",
         "type": "choice",
         "choices": {
           "text": { "type": "string" },
           "count": { "type": "uint32" }
         }
       }
     },
     "required": [],
     "additionalProperties": false
   }

   Empty maps to {}; selected zero maps to {"result":{"count":0}}.
   Numbers 4 and 9 need metadata.  Preservation claims MUST qualify
   wrapper states, unset oneofs, enum openness, and external validation,
   and distinguish decoded values from binary or ProtoJSON
   compatibility.

7.  XML Schema (XSD)

   This section uses XSD 1.1 [XSD-STRUCTURES] [XSD-DATATYPES].  XSD 1.0
   profiles MUST diagnose unavailable assertions, timezone constraints,
   and other features.  An expanded name combines a namespace URI and a
   local name, independent of the namespace prefix.  Instances comprise
   expanded names, typed content, and relevant order; namespace prefixes
   MUST resolve before reference mapping.

   or validation are needed.  UUID [RFC9562] and JSON Pointer lack
   built-in types.

7.1.2.  XML Text and Binary Values

   XML 1.0 cannot carry U+0000.  Out-of-repertoire characters MUST be
   rejected or reversibly encoded, for example as Base64 UTF-8.
   Escaping MUST account for line-ending and attribute normalization,
   not just < and &.

   Binary bindings supply octets; binary length facets count octets, not
   encoded text.  Compression/media-type metadata MUST NOT trigger
   decompression without a selected transformation.

7.1.3.  Objects, Properties, and Nullability

   Objects use complex types with xs:all singleton property elements:
   minOccurs is 1 when required, 0 otherwise; maxOccurs is 1.
   Collections stay inside property containers (Section 7.1.4).
   Nullable elements use nillable="true"; absent, nilled, and empty non-
   nilled states MUST remain distinct.  Null-only types MUST enforce
   nil-only behavior or diagnose widening, not become unrestricted
   strings.

   Closed objects MUST NOT gain unrestricted wildcards.  Open objects
   need key/value collections; bindings MUST preserve arbitrary string
   keys and prevent declared-property collisions. xs:any requires
   separate treatment of expanded names, namespaces, and
   processContents, not an assumed JSON-map equivalence.

   Explicit layouts MAY use attributes, which cannot be nilled or carry
   arbitrary complex values.  Nullable attributes need carriers or
   restrictions.  Round trips MUST retain node kinds and expanded names.

7.1.4.  Arrays, Maps, Tuples, and Choices

   Arrays contain item sequences with occurrence bounds, unbounded when
   no maximum exists.  Item and container nullability are independent;
   optional containers distinguish absence from emptiness.  Sets need
   equivalent JSON-equality validation; scalar xs:unique MUST NOT claim
   arbitrary-value uniqueness.

   Maps contain repeated entry elements with text key and typed value
   children, including empty/punctuated keys within the character
   repertoire.  Supported xs:unique MUST enforce key uniqueness with
   namespace-correct paths.  Tuples use xs:sequence in positional order,
   each occurrence exactly one.  Tagged choices use xs:choice occurring
   exactly once, with singleton tagged elements.  Inline choices need
   materialized branches and exact selector correlation.

7.1.5.  Facets, Inheritance, and Names

   Bounds, lengths, and enumeration facets require matching value
   spaces, units, and whitespace behavior.  Node-defaulting fixed MUST
   NOT substitute for general const.  ECMAScript patterns MUST be
   translated to equivalent XSD matching or reported unsupported.

   Compatible abstract types and inheritance MAY use XSD derivation;
   extension appends XML content, not unordered properties.
   Materialization must retain or report inheritance identity.
   Namespace-URI correspondence MUST be explicit; expanded names are
   URI/local-name pairs, requiring reversible legal identifiers.
   Descriptions use xs:documentation; identified xs:appinfo or companion
   metadata MAY retain other annotations without enforcing them.

7.2.1.  Simple Types

   Processors MUST identify lexical versus post-validation values;
   normalized whitespace cannot claim lexical recovery.  Lists become
   arrays only with defined tokenization/item mappings.  Union member
   identity MUST survive where assigned; overlap cannot be assumed
   harmless.  QName values need namespace bindings or URI/local-name
   carriers.

7.2.2.  Elements, Attributes, and Content Models

   Selected global elements become roots; global collections MUST NOT
   select an arbitrary first root.  Element/type identities MUST remain
   separate.  Elements and attributes become properties under the
   presence rules above; containerless repeated particles become bounded
   arrays, including empty arrays.  Required attributes are non-null.
   Node roles/namespaces MUST survive, with distinct identifiers for
   same-local-name attributes and elements.

   Simple content with attributes needs a dedicated value property whose
   name MUST avoid collisions and identify its synthetic role.
   Compatible xs:all singletons become unordered objects; fixed
   sequences can be tuples, otherwise ordering needs a carrier or loss
   report.  Distinguishable choices become tagged choices, optional or
   repeated as needed; multi-element branches MUST NOT become unrelated
   leaves.

   Mixed content needs an explicit XML-content profile: ordered tagged
   text/element events retaining names and values, not unordered
   properties or concatenated text.

7.2.3.  XML-Specific Semantics

   Validation can add default values and type information; this is
   called augmentation.  Processors MUST state default/augmentation
   state, not claim original absence from defaulted nodes.  Substitution
   groups, xsi:type, type alternatives, wildcard namespaces,
   processContents, identity constraints including xs:keyref, and
   assertions MUST receive equivalent representations or loss
   diagnostics. xs:anyType needs a defined XML-to-JSON representation
   for attributes and mixed content.

7.3.  Example and Preservation Boundary

   Required name and optional nullable age use:

   <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
     <xs:element name="Person">
       <xs:complexType>
         <xs:all>
           <xs:element name="name" type="xs:string"/>
           <xs:element name="age" type="xs:int"
                       minOccurs="0" nillable="true"/>
         </xs:all>
       </xs:complexType>
     </xs:element>
   </xs:schema>

   Either child order is valid.  Omission means absence; <age
   xsi:nil="true"/> means present null with xsi bound to
   http://www.w3.org/2001/XMLSchema-instance; empty non-nilled age is
   invalid.

8.  CDDL

   CDDL [RFC8610] processors MUST identify JSON versus Concise Binary
   Object Representation (CBOR) [RFC8949] interpretation.  CBOR adds
   octets, tags, undefined, non-finite floats, and non-text keys.
   Additional controls, including [RFC9165], need identified, enforced
   vocabularies.

   The primary profile binds native CBOR logical values.  Core's
   existing CBOR mapping instead follows Section 8.3, except binary uses
   bstr; wide integers and decimals are not wire-compatible with this
   native profile.  Processors MUST identify the binding, not infer it
   from the media type.

8.1.  JSON Structure to CDDL

8.1.1.  Primitive Types in the CBOR Profile

   +==============================+====================================+
   | JSON Structure type          | CDDL representation                |
   +==============================+====================================+
   | null                         | nil                                |
   +------------------------------+------------------------------------+
   | boolean                      | bool                               |
   +------------------------------+------------------------------------+
   | string                       | tstr                               |
   +------------------------------+------------------------------------+
   | integer, int8, uint8,        | The exact integer range in         |
   | int16, uint16, int32,        | Section 3.7                        |
   | uint32                       |                                    |
   +------------------------------+------------------------------------+
   | int64, uint64                | The exact integer range in         |
   |                              | Section 3.7                        |
   +------------------------------+------------------------------------+
   | int128, uint128              | Bounded native integers and tagged |
   |                              | bignums as specified below         |
   +------------------------------+------------------------------------+
   | float                        | float32, with a JSON-compatible    |
   |                              | finite domain                      |
   +------------------------------+------------------------------------+
   | double                       | float64, with a JSON-compatible    |
   |                              | finite domain                      |
   +------------------------------+------------------------------------+
   | float8                       | A wider float carrier with         |
   |                              | retained source restrictions       |
   +------------------------------+------------------------------------+
   | number                       | number, only over its exactly      |
   |                              | representable subset               |
   +------------------------------+------------------------------------+
   | decimal                      | Tag 4 decimal fraction with        |
   |                              | compatible numeric restrictions,   |
   |                              | or an explicit alternative carrier |
   +------------------------------+------------------------------------+
   | binary                       | bstr                               |
   +------------------------------+------------------------------------+
   | date, time, datetime,        | tstr with the source temporal      |
   | duration                     | restrictions                       |
   +------------------------------+------------------------------------+
   | uuid, uri,                   | tstr with the source semantic      |
   | jsonpointer                  | restrictions                       |
   +------------------------------+------------------------------------+
   | any                          | A JSON-compatible recursive value  |
   |                              | rule, not unrestricted CBOR any    |
   +------------------------------+------------------------------------+

                                  Table 10

   CBOR int spans -18446744073709551616..18446744073709551615; narrower
   Core bounds MUST survive. uint .size n bounds values, not encoded
   width.  The complete 128-bit domains use:

   js-uint128 = uint / #6.2(bstr .size (0..16))

   js-b127 = (bstr .size (0..15)) /
             ((bstr .size 16) .bits (0..6 / 8..127))

   js-int128 = int / #6.2(js-b127) / #6.3(js-b127)

   Tag 2 carries unsigned big-endian n; tag 3 means -1-n.  For signed
   16-octet magnitudes, .bits excludes first-octet bit 7, limiting n to
   2^127-1.  Larger byte strings are excluded even with redundant
   zeroes.  Explicit tstr alternatives MAY be used but MUST enforce
   grammar and bounds.

   CDDL number admits integers/floats, not arbitrary JSON decimals;
   silent rounding MUST NOT occur.  Tag-4 alternatives MAY use
   representable exponent and mantissa components.  Decimal bindings
   MUST enforce effective precision, scale, and bounds on
   mantissa*10^exponent, with compatible digit semantics; unconditional
   float64 is forbidden.  Tool-limited text alternatives need exact
   parsing/formatting, not a choice based on Core's JSON spelling.

   Binary binds to octets.  Semantic tags MAY use declared profiles
   whose identity and content MUST be checked; tag-0 text does not
   validate [RFC3339] syntax.  Core any MUST use recursive JSON-
   compatible arrays, text-keyed maps, and supported scalars, excluding
   undefined, non-finites, and arbitrary tags unless explicitly
   represented reversibly.

8.1.2.  Maps and Presence

   Objects use literal text keys: occurrence one for required, ? for
   optional, and / nil for nullable:

   presence-example = {
     "required": tstr,
     ? "optional": tstr,
     "required-nullable": tstr / nil,
     ? "optional-nullable": tstr / nil
   }

   Closed objects omit wildcards; open objects add projected extra-value
   rules.  Known keys MUST use cuts, supplied by literal-key colon
   notation, to prevent wildcard bypass.  Here the cut commits level to
   0..255; a string-valued level cannot fall back to the wildcard:

   open-reading = {
     ? "level": 0..255,
     * tstr => any
   }

   Here any requires a full-CBOR extra-value profile; Core
   additionalProperties: true MUST instead use Section 8.1.1' recursive
   JSON domain.

   Maps use { * tstr => V }. Bindings MUST reject duplicate logical keys
   and MUST NOT add numeric/tagged keys.  Alternative required sets MUST
   enforce exactly-one-complete-set semantics or report residual
   validation.

8.1.3.  Arrays, Tuples, Unions, and Choices

   Arrays use [* T], bounded [m*n T], or open occurrence ranges.  Tuples
   fix members in tuple order, retaining names as metadata.  Sets need
   residual JSON-equality uniqueness retained or reported; distinct map
   keys MUST NOT substitute for arbitrary-value set equality.

   Unions use /, retaining order/selection policy for overlapping Core
   branches.  Tagged choices use closed singleton maps; inline choices
   require literal selectors in materialized maps, not optional
   unconstrained strings.  Named types become rules.  Finite-valued
   recursion MAY survive; processors MUST NOT replace cycles with any or
   reject all recursion because of cycles.

8.1.4.  Controls and Annotations

   Compatible bounds use ranges/comparisons.  Exclusive integer limits
   MAY shift by one using exact arithmetic; floating/decimal limits MUST
   NOT.  Constants/enums use literals/type choices and MUST follow the
   instance binding.

   Text .size counts UTF-8 octets: U+00E9 is one character, two octets.
   Character limits MUST NOT be copied without unit equivalence. .regexp
   needs ECMAScript-to-XSD translation; all chained constraints MUST
   survive through controlled types or intersections. .cbor/.cborseq
   constrain decoded content, unlike media-type annotations.

   Round-trip metadata includes groups, generics, sockets, and comments
   within scope; altnames.cddl retains rule spelling only.

         | nil, null         | null                              |
         +-------------------+-----------------------------------+

         | bstr, bytes       | binary with an encoding adapter   |

         +-------------------+-----------------------------------+

         |                   | negative range                    |
         +-------------------+-----------------------------------+
         | int               | int128 with the exact native-     |

   nint bounds -18446744073709551616..-1 MUST survive; int uses

   Carrier width MUST NOT replace source bounds.  Widened float16 needs
   representability constraints, not just magnitude limits.

   Undefined MUST NOT become null.  Unknown tags MUST NOT disappear.
   Tagged-value profiles MAY use tag-number/payload objects or tuples
   but MUST retain distinctions.  Tag-4 decimals, tag-0 date-time, tag-1
   epoch time, and binary UUIDs MUST retain their individual semantics,
   ranges, and representations.  Prelude time is not Core [RFC3339]
   time-of-day.

8.2.2.  Structures and Evaluation

   Known text keys become objects; homogeneous text-keyed maps become
   maps.  Other keys need typed entries or rejection: stringifying 1 and
   "1" collapses identity.  Occurrences determine presence/bounds; nil
   means null, not absence.  Repeated arrays become arrays; fixed groups
   become named tuples.  Variable, optional, or repeated-group layouts
   MUST retain adapters/validation or be rejected.

   / is an inclusive type choice.  A group choice // selects a complete
   group of entries. // MUST preserve groups, not unrelated leaves. &(a:
   1, b: 2) enumerates 1 and 2, with metadata labels. ~ MUST be
   evaluated before projection, not interpreted as inheritance.
   Generics MAY be materialized; generic declarations within the claimed
   round-trip scope MUST survive. /=///= extensions and sockets MUST be
   assembled first; unknown required controls, unresolved sockets, or
   unavailable feature conditions prevent losslessness.

   Size, regexp, intersection, and decoded-content semantics MUST
   survive. .cbor MUST NOT become only a media-type annotation;
   decoding/re-encoding MUST NOT claim original octet preservation.

8.3.  JSON Representation Profile

   JSON profiles MUST use Core encodings: binary as encoded tstr, wide
   integers and decimals as grammar/range-constrained tstr, small
   integers as bounded JSON numbers.  Floating constraints concern JSON
   values, not CBOR widths.  Tags, undefined, non-finites, and non-text
   keys need separate JSON encodings or exclusion.  RFC 8610 limits JSON
   numeric precision; accepted subsets or alternative carriers MUST be
   identified.  Switching native/JSON profiles transforms instances, not
   necessarily logical values.

8.4.  Example and Preservation Boundary

   A sequence and binary payload:

   {
     "$schema": "https://json-structure.org/meta/core/v0/#",
     "$id": "https://example.com/schemas/Frame",
     "name": "Frame",
     "type": "object",
     "properties": {
       "sequence": { "type": "uint64" },
       "payload": { "type": "binary" }
     },
     "required": ["sequence", "payload"],
     "additionalProperties": false
   }

   project to native CBOR:

   frame = {
     "sequence": 0..18446744073709551615,
     "payload": bstr
   }

   Native bindings round-trip 18446744073709551615 and payload octets.
   JSON instead uses constrained digit text and Base64; width/encoding
   identity needs metadata.

9.2.  Loss Reporting

   Reports MUST distinguish exact types from wider carriers, and
   rejection from successful projection of a restricted domain.  Hidden
   restrictions cannot justify lossless claims.

10.  Security Considerations

   Applications MUST NOT rely on discarded constraints without
   replacement validators.  Resolvers SHOULD use explicit retrieval
   policies, trusted contexts, and limits; loading XSD MUST NOT enable
   XML external entities.

   Implementations SHOULD bound regex matching and reject unverified
   translations.  Recursion, bounds, generic expansion, bignums, and
   exponent expansion SHOULD have resource limits reported as failures,
   not truncation or type substitution.

   Implementations MUST distinguish content annotations from processing
   requests and SHOULD limit decoded size and nesting depth.  Metadata,
   alternate names, and field-number correspondences MUST be treated as
   untrusted and checked for collisions, illegal identifiers, reserved
   numbers, and inconsistent declarations.
