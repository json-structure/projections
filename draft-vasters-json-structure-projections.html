JSON Structure: Schema Projections

Abstract

This document projects the representation-neutral JSON Structure model into JSON Schema, Apache Avro, Protocol Buffers, XML Schema, and Concise Data Definition Language (CDDL). It defines target schemas, serializer value bindings, reverse imports, and conditions for preserving values, constraints, and schema information.¶

1. Introduction

JSON Structure [JSTRUCT-CORE] is intended as a representation-neutral definition language. Its schemas are written in JSON [RFC8259] and include provisions for JSON serialization, but its data definitions can be used independently of that representation.¶

JSON Structure serves as the canonical, abstract base model for data definitions. Data structures are defined in JSON Structure and projected into programming languages, database schemas, and other schema languages. This document covers projections into formal schema languages.¶

To serialize data in Avro, an application projects its JSON Structure data definition into an Avro schema and uses an Avro serializer with that schema. The same approach applies to Protocol Buffers and the other formats covered here: their schemas are projections of the data model contained in the JSON Structure definition. Reverse imports recover JSON Structure definitions within the stated preservation limits.¶

The targets are JSON Schema [JSONSCHEMA-CORE] [JSONSCHEMA-VALIDATION], Avro [AVRO], Protocol Buffers [PROTO2] [PROTO3], XML Schema (XSD) [XSD-STRUCTURES] [XSD-DATATYPES], and CDDL [RFC8610].¶

The rules use Validation [JSTRUCT-VALIDATION], Conditional Composition [JSTRUCT-COMPOSITION], and Alternate Names [JSTRUCT-ALTNAMES] where needed.¶

2. Conventions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

The model is the canonical data model defined by a JSON Structure schema document. A projection maps that model into another schema language. Source and target follow the conversion direction. A binding maps model values to and from the serializer's data API. A carrier holds a value lacking an equivalent target type. Projection rules specify schema mappings, bindings, and preservation limits.¶

The applicable Core version is identified by $schema. A processor MUST report any substitution of another version's semantics.¶

3. Projection and Preservation Model

3.1. Canonical Definitions and Serialization Bindings

A projection MUST specify target schemas and bindings from logical types, not JSON tokens. Decimals are exact base-10; binary values are octets.¶

Native types SHOULD be used when value-preserving. Textual or wrapped carriers require a target or serializer limitation, or an explicit representation-preserving profile. The reason and consequences MUST be stated. The model remains authoritative: a binding or identified validator MUST enforce constraints absent from the target when preservation is claimed. Validation outside the generated target schema is called residual validation.¶

Core JSON encodings apply only to selected JSON representations or boundaries, including JSON Schema and the CDDL JSON profile. They MUST NOT be imposed on native bindings.¶

3.2. Instances and Value Equivalence

Let S be the set of valid source values and T the set of target values. Encoding E maps S into T; decoding D maps target values back to the source model. Value preservation requires D(E(x)) = x for every x in S.¶

Equality follows the source model: object and set order is irrelevant; array and tuple order matters. Absence, present null, and present empty collections differ. Numeric equality is exact; binary equality compares octets; string equality compares characters.¶

Logical values MUST be distinguished from lexical spellings. Trailing decimal zeroes, equivalent binary-text spellings, token whitespace, XML prefixes, unordered schema members, and comments need not survive unless lexical or source-file preservation is requested.¶

Temporal bindings MUST identify calendar, offset-bearing, or instant semantics. Discarding an observable offset loses information. An explicit instant profile permits UTC normalization, without preserving original text.¶

3.3. Independent Preservation Properties

Value preservation:

Every valid source value is reversible, even if its carrier changes.¶

Constraint preservation:

The target schema accepts exactly the encodings of valid source values, E(S), with no additional values. Constraints checked only by an adapter are not native target-schema constraints.¶

Schema round-trip preservation:

Import recovers semantic declarations: types, references, names, constraints, defaults, and identities. Claims MUST state required metadata.¶

Unqualified lossless requires all three for the stated subset and profile. Partial claims MUST be qualified. For example, int8 in unrestricted Avro int preserves values, widens constraints, and needs metadata to recover width.¶

3.4. Processing Profiles and Diagnostics

A processor MUST identify dialects, roots, extensions, and required adapters, validators, or metadata. Unmet lossless requests MUST fail; explicitly enabled lossy projections MAY proceed. Every applicable loss MUST be reported at its affected source location. Every loss diagnostic MUST identify source format and location, target construct or omission reason, affected preservation property, effect, and any remedy or source restriction. Effects distinguish widening (admitting additional values), narrowing (excluding source values), value collapse (merging distinct values), representation change, and schema loss.¶

Ignored annotations MUST NOT count as enforcement. Unknown types and unresolved references MUST NOT silently become permissive types or defaults. Diagnostic interfaces and metadata formats are implementation-defined; interoperable round-trip claims MUST use an agreed metadata channel and interpretation.¶

3.5. Roots, Namespaces, and References

Processors MUST select root type or $root; definitions-only libraries MUST NOT acquire arbitrary roots. A target requiring one root needs explicit selection. References use {"type":{"$ref":"..."}}, or {"$ref":"..."} inside union arrays. Bare schema $ref and referenced root type are invalid; referenced roots use $root.¶

References MUST resolve before name rewriting, with JSON Pointer escaping per [RFC6901] and identity preserved. Supported recursion MUST remain references; unsupported recursion MUST be diagnosed, not depth-truncated. External resources MAY be materialized or use Import [JSTRUCT-IMPORT]; resource identity and resolution MUST survive.¶

3.6. Names and Annotations

Imported names MUST map to distinct legal JSON Structure identifiers matching [A-Za-z_][A-Za-z0-9_]*. A declaration's altnames map MAY retain names for other representations. Its json entry gives the JSON property name; avro, proto, xml, and cddl give format-specific names. A projection uses the entry for its target format.¶

For example, this schema gives the model property firstName different JSON and Avro names:¶

{
  "$schema": "https://json-structure.org/meta/extended/v0/#",
  "$id": "https://example.com/schemas/Person",
  "$uses": ["JSONStructureAlternateNames"],
  "name": "Person",
  "type": "object",
  "properties": {
    "firstName": {
      "type": "string",
      "altnames": {
        "json": "first-name",
        "avro": "first_name"
      }
    }
  },
  "required": ["firstName"],
  "additionalProperties": false
}
¶

The Avro record field is named first_name; the JSON property is first-name. The model's required array still names firstName. Alternate names specify spelling, not encoding, field numbers, XML node kinds, or namespace identity. Target names MUST satisfy the format's naming and uniqueness rules.¶

required and tuple name declaration keys; references MUST be rewritten consistently. altenums mappings MUST be one-to-one. Descriptions SHOULD be copied to target documentation. Examples, units, currencies, localized descriptions, semantic annotations, and unknown extensions MUST be retained as metadata or reported lost.¶

3.7. Numeric and Textual Representations

integer aliases int32. A b-bit signed integer spans -(2^(b-1)) through 2^(b-1)-1; an unsigned integer spans 0 through 2^b-1.¶

uint8 0 255
int16 -32768 32767
uint16 0 65535
int32, integer -2147483648 2147483647
uint32 0 4294967295

uint64 0 18446744073709551615

Core JSON uses numbers through uint32, strings for wider integers and decimal, and encoded text such as Base64 [RFC4648] for octets. Schema numeric constraints follow those representations but MUST be applied numerically. Signed integer strings match -?(0|[1-9][0-9]*), unsigned strings (0|[1-9][0-9]*), over the entire string; bounds remain additional.¶

Core decimals require a fractional part. Projections MUST apply effective precision and scale, defaulting to 34 significant and 7 fractional digits. These MUST be reconciled with target coefficient-digit or fixed-scale rules.¶

Generic number MUST NOT be assumed binary64. Floating conversion preserves only exactly representable values; overflow, underflow, and rounding lose values. float8 specifies no portable E4M3, E5M2, or binary16 encoding; processors MUST NOT infer one. Wider carriers lose type identity. Reverse projections MUST handle NaN, payloads, and infinities separately.¶

Character lengths, decoded octet lengths, encoded byte lengths, and numeric precision MUST NOT be interchanged.¶

3.8. Presence, Defaults, and Composition

For non-null T:¶

Table 2
Declaration Permitted states
Required T A present non-null value
Optional T Absence or a present non-null value
Required union of null and T A present null or non-null value
Optional union of null and T Absence, a present null, or a present non-null value

Presence states MUST remain distinct. Default application MUST be evaluated separately; defaults do not imply nullability.¶

Core unions select the first matching member when several members accept a value. Losing that branch identity affects round trips. An inclusive union accepts any matching branch; an exclusive union requires exactly one match. Inclusive unions MUST NOT become exclusive unless disjoint. Alternative required sets mean exactly one complete set; projections MUST preserve this condition, not flatten the sets.¶

Materialization expands inherited declarations into explicit properties. Inheritance and add-ins MUST follow source semantics. Materialization MAY be used after Core's first-base-wins property precedence. Derived properties MUST NOT redefine inherited properties. Conjunctive constraints MUST remain conjunctive without replacing that precedence. Unrepresentable abstractness, inheritance, or add-in identity MUST be reported.¶

4. JSON Schema

This projection validates Core JSON representations using Draft 2020-12. Earlier dialects MUST be normalized, including Draft-07 tuple items, additionalItems, definitions, and older boolean exclusiveMinimum.¶

4.1. JSON Structure to JSON Schema

4.1.1. Primitive Types

Targets MUST identify the 2020-12 $schema. Table mappings include the qualifications below.¶

Table 3
JSON Structure type JSON Schema representation
null {"type":"null"}
boolean {"type":"boolean"}
string {"type":"string"}
number {"type":"number"}
integer, int8, uint8, int16, uint16, int32, uint32 integer with the inclusive bounds in Section 3.7
int64, uint64, int128, uint128 string with the integer grammar and the applicable bounds
float8, float, double number, with source-domain restrictions when expressible
decimal string with the decimal grammar, precision, and scale
binary string with contentEncoding and optional contentMediaType
date string, format: "date"
datetime string, format: "date-time"
time string, format: "time"
duration string, format: "duration"
uuid string, format: "uuid"
uri string, format: "uri-reference"
jsonpointer string, format: "json-pointer"
any An unconstrained schema, such as {} or true

Numeric keywords do not constrain strings; string-valued bounds MUST NOT be copied into them. Integer-string ranges MAY use exact regular expressions; otherwise their bounds MUST be retained for additional validation and native widening reported. Decimal grammar, precision, scale, and bounds require equivalent enforcement. A numeric carrier is a separate instance-transforming profile.¶

By default, format is an annotation; its presence does not require a validator to check that format. Extended types need an agreed assertion profile or equivalent constraints; otherwise their domains widen. uri-reference preserves Core's relative references; uri excludes them.¶

Content annotations do not require decoding or validation. Core's default binary encoding MUST be explicit. contentCompression requires metadata or a loss report.¶

4.1.2. Objects, Maps, and Collections

Objects recursively map properties and required using JSON alternate names. Effective additionalProperties MUST be explicit, including version-defined defaults and recursively projected schema values. Alternative required sets MUST add oneOf branches {"required": Ri} to the common object schema. Ri denotes one alternative set of required property names.¶

Maps use object without declared properties and projected values as additionalProperties. keyNames becomes propertyNames; patternKeys becomes patternProperties only with equivalent additional-property behavior.¶

Arrays project items; sets add uniqueItems: true, without suppressing observable JSON array order. Tuples use prefixItems in tuple order and MUST set minItems: n, maxItems: n, and items: false. Names need metadata.¶

4.1.3. Unions and Choices

Unions use anyOf. Equivalent unrestricted alternatives MAY use a type array. Branch order SHOULD survive; JSON Schema validation does not assign Core's first-match identity.¶

Tagged choices use oneOf branches with properties: {k: V}, required: [k], and additionalProperties: false. Inline choices use materialized alternatives; each MUST require its selector and constrain it with const. Base and branch properties MUST be combined before closure.¶

4.1.4. Constraints, Definitions, and Defaults

These keywords map directly only with matching applicability, representation, and evaluation: minimum, maximum, exclusiveMinimum, exclusiveMaximum, multipleOf, minLength, maxLength, pattern, minItems, maxItems, uniqueItems, contains, minContains, maxContains, minProperties, maxProperties, dependentRequired, and propertyNames.¶

Map entry bounds become property bounds; const and enum retain JSON values. Constraints MUST intersect intrinsic type domains. Conditional Composition MAY use corresponding allOf, anyOf, oneOf, not, if, then, and else with recursively equivalent evaluation.¶

Definitions become uniquely keyed $defs; processors MUST rewrite references and MUST NOT emit namespace-only objects as unconstrained definitions. $root becomes $ref; $id survives when resource identity remains valid. name MAY supply title, not type identity; descriptions map directly. $uses, $offers, abstractness, and namespaces need metadata.¶

JSON Schema default annotates; Validation defaults fill missing properties. This behavioral difference MUST be reported or implemented by a declared adapter.¶

4.2. JSON Schema to JSON Structure

4.2.1. Primitive and Numeric Inference

null, boolean, string, and number map directly. Integer import MUST compute the effective domain, select a containing Core type, and retain narrower constraints. Wide types change JSON numbers to strings. Domains outside all Core integer types MUST be rejected in constraint-preserving Core-only requests; other profiles can use an explicit numeric-text adapter.¶

Integral 1, 1.0, and 1e0 satisfy JSON Schema integer validation. Processors MUST distinguish parsed-value preservation from Core's lexical integer restrictions. Numeric formats MUST NOT independently justify narrowing or representation changes. String formats MAY select extended types only when asserted and domain-compatible; otherwise they remain annotations. Absolute uri restrictions MUST survive. Digit strings MUST remain strings without declared numeric semantics.¶

4.2.2. Structural Mapping

Declared properties become an object; dynamic objects become maps. Unconstrained objects use map-of-any. An object that permits no properties, whose only value is {}, uses Validation maxEntries: 0, not null. Undeclared required names need any declarations plus applicable pattern and additional-property constraints.¶

JSON Schema excludes pattern-matched keys from additionalProperties; Core patterns do not declare properties. Processors MUST construct equivalent key/value rules or diagnose unsupported combinations. Multiple pattern matches intersect.¶

Homogeneous arrays remain arrays, retaining uniqueness constraints. Conversion to sets MAY occur only under an explicit order-discarding, value-collapsing profile. prefixItems becomes a tuple only with exact length and no tail; names MUST be generated or recovered. Other prefixes MUST retain equivalent rules or be rejected, not fixed-length by assumption.¶

4.2.3. Composition and Unsupported Evaluation Features

true becomes any; false requires rejection or Conditional Composition {"type":"any","not":{"type":"any"}}. Missing type MUST preserve category-specific keyword applicability and unconstrained categories.¶

anyOf MAY become a type union when all branches declare types and selection adds no observable distinction. oneOf needs disjointness for inclusive conversion; required-set forms follow Section 4.1.2. allOf MUST retain intersections, including contradictions; structural merging requires equivalence, never property overwrites.¶

$dynamicRef, $dynamicAnchor, unevaluatedProperties, and unevaluatedItems MUST be transformed equivalently for the selected graph or rejected in lossless mode. References, anchors, nested $id, and vocabularies MUST resolve before conversion. Unknown required vocabularies prevent lossless claims.¶

4.3. Example and Preservation Boundary

This closed object:¶

{
  "$schema": "https://json-structure.org/meta/core/v0/#",
  "$id": "https://example.com/schemas/Reading",
  "name": "Reading",
  "type": "object",
  "properties": {
    "label": { "type": "string" },
    "level": { "type": "uint8" },
    "note": { "type": ["null", "string"] }
  },
  "required": ["label", "level"],
  "additionalProperties": false
}
¶

projects to:¶

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.com/schemas/Reading",
  "title": "Reading",
  "type": "object",
  "properties": {
    "label": { "type": "string" },
    "level": { "type": "integer", "minimum": 0, "maximum": 255 },
    "note": { "anyOf": [{ "type": "null" }, { "type": "string" }] }
  },
  "required": ["label", "level"],
  "additionalProperties": false
}
¶

Presence and bounds survive; recovering original width requires metadata.¶

5. Apache Avro

This section uses Avro 1.12.0 [AVRO], excluding remote procedure calls, container compression, and registry identifiers. Non-record roots are legal; wrappers for surrounding-system restrictions MUST be separately declared.¶

5.1. JSON Structure to Avro

5.1.1. Primitive Types

Table 4
JSON Structure type Avro carrier Qualification
null null Same null value
boolean boolean Same value set
string string Same Unicode text values
integer, int32 int Same signed 32-bit domain
int8, int16, uint8, uint16 int Source range is not enforced natively
uint32 long Full value domain fits; unsigned bound is not native
int64 long Native signed 64-bit integer
uint64 bytes with logicalType: "decimal" Precision 20, scale 0; retain unsigned 64-bit bounds
int128 bytes with logicalType: "decimal" Precision 39, scale 0; retain signed 128-bit bounds
uint128 bytes with logicalType: "decimal" Precision 39, scale 0; retain unsigned 128-bit bounds
float8, float float Exact-value and source-domain qualifications apply
double, number double Generic numbers can lose precision

decimal bytes with logicalType: "decimal" Derive compatible precision and scale

uint64 MUST NOT use long unless an explicit restricted profile fits its signed range. Wide integers use Section 5.1.2.¶

5.1.2. Wide Integers

The standard projection MUST use decimal on bytes, scale 0, precision 20 for uint64 and 39 for either 128-bit type. The exact integer is the unscaled coefficient: signed big-endian two's complement, including a leading zero octet when needed for a positive value. Avro supplies the byte-count prefix.¶

{
  "type": "record",
  "name": "WideIntegers",
  "namespace": "example",
  "fields": [
    {
      "name": "unsigned64",
      "type": {
        "type": "bytes", "logicalType": "decimal",
        "precision": 20, "scale": 0
      }
    },
    {
      "name": "signed128",
      "type": {
        "type": "bytes", "logicalType": "decimal",
        "precision": 39, "scale": 0
      }
    },
    {
      "name": "unsigned128",
      "type": {
        "type": "bytes", "logicalType": "decimal",
        "precision": 39, "scale": 0
      }
    }
  ]
}
¶

A declared fixed profile MAY substitute at least 9 octets for precision 20 or 17 for precision 39. A 16-octet precision-39 declaration is invalid. Bindings or validators MUST enforce original bounds, including unsigned non-negativity. Unsupported precision MUST fail, not round, truncate, or pass through binary64. Reconstruction MUST retain integer identity and bounds; decimal parameters cannot distinguish the two 128-bit types.¶

5.1.3. Logical Types

Logical types MUST use their specified carriers: decimal on bytes/fixed, date and time-millis on int, timestamps on long. Unknown annotations are ignored by ordinary readers.¶

An Avro decimal has precision p and scale s; its value is coefficient times 10^(-s). Projections MUST derive compatible p > 0 and 0 <= s <= p from effective source constraints, without rounding; otherwise they MUST declare an alternative carrier or reject lossless native conversion. Decimal text needs numeric validation.¶

For n-octet fixed, precision cannot exceed floor(log10(2^(8*n-1)-1)). Size, padding, and sign extension MUST conform. Core decimal output MUST restore a fractional part, including .0 at scale zero; lexical zeroes need not survive.¶

  • date: signed days since 1970-01-01, within both calendar domains.¶

  • time-millis/time-micros: offset-free time since midnight; Core full-time has an offset. Dropped offsets or fractions are losses.¶

  • timestamp-millis/timestamp-micros/timestamp-nanos: signed epoch counts. Bindings MUST check range, precision, and leap seconds under a declared instant policy; original offsets and text do not survive.¶

  • local-timestamp-millis/local-timestamp-micros/local-timestamp-nanos: no zone; UTC MUST NOT be assumed.¶

  • duration: unsigned little-endian uint32 months, days, and milliseconds in 12 octets, not a general signed duration.¶

Unmatched temporal bindings MUST identify preserved components and validate temporal text.¶

5.1.4. Records, Optionality, and Collections

Objects become records, properties become fields, and namespaces remain distinct. Recursive records MUST follow legal Avro definition order. Open objects need an extra-properties map with externally enforced collision exclusion; Avro records have no additionalProperties.¶

Every field has a value. For non-null T:¶

Table 5
Source property Avro field representation
Required T T
Required nullable T Union of null and T
Optional T Union of null and T; null represents absence
Optional nullable T Union of null and a named present-value record whose value field has union type null and T

In the last row, outer null means absence. A present record whose value is null means present null.¶

Wrapper names MUST be unique. Optional fields MAY default to null with null first. Optional-nullable flattening to ["null", T] MUST report value collapse; other null-as-absence bindings require source correspondence.¶

Arrays and string-keyed maps project recursively. Sets use arrays with external uniqueness; collection bounds need validation. Tuples use fields in tuple order; names and order MUST survive, without inferring object identity.¶

5.1.5. Unions, Choices, and Enumerations

Direct nested unions and duplicate unnamed branch kinds require distinct named record wrappers. Processors MUST add these where necessary and apply Core first-match selection before choosing the Avro branch.¶

Tagged choices SHOULD use distinct named one-field records, unwrapped on import. A discriminator plus independent union needs correlation validation. Inline choices use materialized branch records; selectors MUST be restored. Defaults do not enforce selector constants.¶

String enums require legal unique symbols or reversible mappings. Numeric enums MUST NOT become symbols without explicit transformation. const, patterns, lengths, narrower bounds, required-set alternatives, and composition generally need validation beyond Avro.¶

5.1.6. Extensible Values and Schema Evolution

The projection of any uses different reader and writer schemas. The generic reader includes an empty named record in its union. A concrete writer adds typed fields to that record without changing the reader. Primitive, array, or map branches MAY predeclare understood categories; they do not close the source domain.¶

Union order and promotions matter: string can resolve as bytes, or vice versa. Value-preserving bindings MUST use named wrappers or retain writer-branch identity and its exact inverse, not infer categories from resolved values.¶

Each extensible position MUST have a stable unique full name; writers MUST retain it and enclosing reader compatibility. Unmatched new union branches fail resolution. Written fields MUST have concrete types; decoding MUST use the actual writer schema as well as the reader.¶

5.2. Avro to JSON Structure

5.2.1. Types and Names

Primitives map directly, except int -> int32, long -> int64, and bytes -> binary. Non-finite values need tagged representations or rejection of the source domain; finite-only restrictions MUST be reported.¶

Records become closed objects with every field required, including nullable or defaulted fields. Empty records use map-of-any with Validation maxEntries: 0; identifying original any needs retained correspondence.¶

Arrays, maps, and named references map directly after full-name resolution. Enums become string enums; round trips retain symbol order. fixed becomes binary with exact octet count; maxLength MUST NOT claim to reconstruct that binary size.¶

Unions MAY become Core unions without required identity loss; otherwise tagged choices MUST retain branches, including int/long distinctions for equal values. Array/map union members require reusable type references.¶

5.2.2. Logical Types and Resolution Metadata

Retained wide-integer bindings MUST recover the declared integer type after checking precision, scale, integrality, and bounds. Otherwise decimal import MUST preserve bounds +/-(10^p-1)*10^(-s) and quantum 10^(-s). The quantum is the difference between adjacent representable decimal values. One exact construction uses Core precision p for s > 0, p+1 for s = 0, scale max(1,s), those bounds, and Validation multipleOf equal to the quantum. For p=2, s=2, bounds are -0.99..0.99 and quantum 0.01. Decimal constraints retain fractional syntax, including .0; documents MUST declare JSONStructureValidation in $uses. Unsupported parameters MUST be diagnosed, not narrowed.¶

Round trips MUST retain carrier size and logical identity. big-decimal MUST use declared variable-scale semantics or report restriction. UUIDs require shared domains; fixed 16-octet versus textual carriers need metadata. Dates MAY use the shared calendar domain; timestamps MAY use explicit UTC formatting with unsupported ranges/fractions rejected or diagnosed. Timezone-free types MUST NOT invent offsets. Durations MAY use uint32 month/day/millisecond objects or tuples; duration text needs semantic and range equivalence.¶

Unknown logical types MUST retain underlying types and annotations; malformed annotations MUST NOT justify recognized Core types. Aliases, field/sort order, enum/field defaults, and resolution rules need metadata. Resolution defaults do not permit omitted writer fields; conversion to Validation defaults MUST qualify behavioral changes. Byte/fixed defaults MUST be decoded by Avro's rules before Core encoding.¶

Processors MUST implement Section 3 and identify format and profile. Support MAY be partial if unsupported constructs are rejected or reported under explicit lossy policies. Verification MUST cover the declared domain, not observed samples.¶

Value tests MUST compare D(E(x)) with x under Section 3.2. Constraint tests MUST include values outside E(S). Schema tests MUST compare semantic declarations within scope, including field numbers, namespaces, and defaults.¶

9.2. Loss Reporting

Reports MUST distinguish exact types from wider carriers, and rejection from successful projection of a restricted domain. Hidden restrictions cannot justify lossless claims.¶

10. Security Considerations

Applications MUST NOT rely on discarded constraints without replacement validators. Resolvers SHOULD use explicit retrieval policies, trusted contexts, and limits; loading XSD MUST NOT enable XML external entities.¶

Implementations SHOULD bound regex matching and reject unverified translations. Recursion, bounds, generic expansion, bignums, and exponent expansion SHOULD have resource limits reported as failures, not truncation or type substitution.¶

Implementations MUST distinguish content annotations from processing requests and SHOULD limit decoded size and nesting depth. Metadata, alternate names, and field-number correspondences MUST be treated as untrusted and checked for collisions, illegal identifiers, reserved numbers, and inconsistent declarations.¶
